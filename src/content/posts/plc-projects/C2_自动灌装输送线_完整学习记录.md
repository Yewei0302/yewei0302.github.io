## 项目定位

C2是在C1交通灯顺控之后完成的一次综合练习。项目不再只验证PLC内部的步序，而是把以下三个部分真正连接起来：

1. TIA Portal V19中的S7-1500控制程序；
2. PLCSIM Advanced与Factory I/O构成的虚拟生产线；
3. WinCC RT Advanced制作的操作与监控画面。

控制对象是一条自动灌装输送线：发射器生成空瓶，输送带将瓶体送至灌装位，系统完成稳定等待、定时灌装和滴漏等待，再把成品送到出口并计数。

> 本项目的三方通信、HMI控制、动态显示和主要工艺步骤已经跑通，学习目标已经完成；但GRAPH的出瓶、离位和重新启动逻辑仍暴露出较明显的设计问题。因此本文把它定义为“完成的学习项目”，而不是可以直接复制到真实设备上的成熟程序。

## 一、项目环境

| 项目 | 配置 |
|---|---|
| 编程软件 | TIA Portal V19 |
| PLC | S7-1500 CPU 1511-1 PN |
| PLC语言 | GRAPH + LAD |
| PLC仿真 | S7-PLCSIM Advanced V6.0 |
| 产线仿真 | Factory I/O中文版 |
| HMI | WinCC RT Advanced |
| PLCSIM实例 | `factoryio` |
| Factory I/O驱动 | Siemens S7-PLCSIM，S7-1500 Advanced模式 |

本项目全部采用软件仿真，没有使用实体PLC、传感器和执行器。文中的急停是普通程序逻辑，只用于学习；真实设备必须使用符合要求的安全回路、安全继电器或安全PLC。

## 二、PLC程序架构

OB1将程序拆分为多个职责明确的块：

| 顺序 | 程序块 | 主要职责 |
|---:|---|---|
| 1 | `FB_Alarm` | 进瓶超时、出瓶超时及综合故障处理 |
| 2 | `FB_ModeControl` | 自动模式、启停、复位和系统允许 |
| 3 | `FB_FillingSequence` | 使用GRAPH执行自动灌装步序 |
| 4 | `FB_Counter` | 完成瓶数计数与手动清零 |
| 5 | `FC_OutputControl` | 统一生成输送带、灌装阀、指示灯等物理输出 |

程序采用“命令—状态—顺控请求—最终输出”的分层思路。GRAPH只产生输送请求、灌装请求和计数脉冲，Q点由`FC_OutputControl`统一写入，避免GRAPH步骤和外围程序同时写同一个输出。

### HMI与现场命令合并

现场按钮和HMI按钮最终都进入统一请求变量：

```text
xStartReq      = xStartPB OR xHMIStartCmd
xStopReq       = xStopPB  OR xHMIStopCmd
xResetReq      = xResetPB OR xHMIResetCmd
xAutoModeReq   = xAutoModeSel OR xHMIAutoModeCmd
xCountResetReq = xCountResetPB OR xHMICountResetCmd
```

调试中曾发现停止请求误接成`xHMIEStopCmd`，导致HMI普通停止按钮没有进入正常停止逻辑。这个问题让我更直观地认识到：变量名称相似时，必须逐网络核对信号用途，不能只看编译是否为0错误。

## 三、GRAPH七步工艺流程

自动流程划分为七个步骤：

| 步骤 | 名称 | 主要动作与转换目标 |
|---|---|---|
| S0 | 待机 | 等待自动模式、系统允许和启动请求 |
| S10 | 进瓶 | 发射工件并启动输送带，等待灌装位传感器 |
| S20 | 稳定 | 瓶体到位后按`tBottleStablePT`等待 |
| S30 | 灌装 | 打开灌装阀并保持`tFillingPT` |
| S40 | 滴漏等待 | 关闭灌装阀并等待`tDripPT` |
| S50 | 出瓶 | 启动输送带，将成品送向出口传感器 |
| S60 | 完成 | 产生计数脉冲并结束本次循环 |

每个步骤通过`N`限定符输出动作，并同步写入`iSeqStepNo`。HMI不直接读取GRAPH内部复杂结构，而是根据`iSeqStepNo = 0/10/20/30/40/50/60`显示当前步号、中文步骤名称和七步流程色块。

### 故障时停止的不只是Q点

如果报警只封锁最终输出，GRAPH仍可能在后台继续跳步。故障解除后，流程可能已经偏离实际设备位置。因此程序增加：

```text
xSequenceOffCmd = NOT xSystemEnableSts
```

并将其送入GRAPH的`OFF_SQ`，使系统失去允许条件时，顺控器与物理输出一起停止。

## 四、I/O与Factory I/O映射

### PLC输入

| 地址 | 变量 | 作用 |
|---|---|---|
| `%I0.0` | `xStartPB` | 现场启动 |
| `%I0.1` | `xStopPB` | 现场停止 |
| `%I0.2` | `xResetPB` | 故障复位 |
| `%I0.3` | `xEStopOK` | 急停回路正常 |
| `%I0.4` | `xAutoModeSel` | 现场自动模式 |
| `%I0.5` | `xBottleAtFillSns` | 灌装位传感器 |
| `%I0.6` | `xBottleExitSns` | 出口传感器 |
| `%I0.7` | `xCountResetPB` | 现场计数清零 |

### PLC输出

| 地址 | 变量 | Factory I/O对象 |
|---|---|---|
| `%Q0.0` | `xConveyorRunCmd` | Belt Conveyor |
| `%Q0.1` | `xFillValveCmd` | 灌装阀指示 |
| `%Q0.2` | `xRunLamp` | 运行指示灯 |
| `%Q0.3` | `xFaultLamp` | 故障指示灯 |
| `%Q0.4` | `xBottleEmitterCmd` | Emitter |
| `%Q0.5` | `xBottleRemoverCmd` | Remover |

Factory I/O场景从空白开始搭建，主要包含一条6 m输送带、两个Diffuse Sensor、Emitter、Remover和指示灯。两个传感器分别映射到`%I0.5`和`%I0.6`。

联调时还遇到一个容易忽略的问题：Factory I/O接管输入区后，未映射的`%I0.3`保持为0，HMI会立即显示急停回路异常。最终把`FACTORY I/O (Running)`映射到`%I0.3`，使场景进入运行状态时急停回路正常。

## 五、WinCC RT Advanced画面

HMI画面分为操作控制、系统状态、设备流程监控、参数设定、步序显示和累计计数六个区域。

![C2最终HMI与Factory I/O联调画面](/images/posts/c2-auto-filling-final.jpg)

### 1. PC站与PLC连接

最初PC站只有`WinCC RT Advanced`，没有网络接口，因此HMI连接页面只能手工填写IP，无法选择PLC伙伴。解决过程是：

1. 在PC站中加入`IE General`；
2. PLC设置为`192.168.0.1`，PC/HMI设置为`192.168.0.2`；
3. 两端加入同一个`PN/IE_1`子网；
4. 在“设备和网络—连接”中，从`HMI_RT_1`建立到CPU的HMI连接。

完成后，HMI变量可以直接使用符号访问，不需要手工填写DB绝对地址。

### 2. 操作变量与按钮事件

主要HMI命令变量包括：

- `xHMIStartCmd`
- `xHMIStopCmd`
- `xHMIResetCmd`
- `xHMIAutoModeCmd`
- `xHMICountResetCmd`
- `xHMIEStopCmd`

普通按钮使用“按下置位、释放复位”，形成瞬时命令。模拟急停使用保持置位，由故障复位按钮清除。调试中如果把“单击置位”和“释放复位”混用，事件执行顺序可能让变量最终停在TRUE，这也是HMI按钮看似松开、PLC命令却持续有效的原因。

### 3. 动态状态与设备监控

系统状态灯连接急停正常、系统使能、系统运行和综合故障变量；设备状态灯直接读取Q0.0、Q0.1、Q0.4和Q0.5对应的符号变量。未激活时为灰色，运行时为绿色，故障时为红色。

原计划使用WinCC自带GRAPH概览控件，但它需要专用的GRAPH数据连接，普通`Int`步号不能直接替代。最终使用`iSeqStepNo`、文本列表和七个动态色块自制流程概览，结构更简单，也能明确显示当前步骤。

### 4. TIME参数显示

五个工艺参数在PLC中均使用`TIME`：

- `tBottleStablePT`
- `tFillingPT`
- `tDripPT`
- `tBottleInTimeoutPT`
- `tBottleOutTimeoutPT`

直接选择WinCC“时间”格式时，持续时间会被当成钟表时间显示。改为十进制格式并把小数点左移3位后，PLC中的毫秒值可以显示成秒：

```text
T#500ms  →  0.500 s
T#1s     →  1.000 s
T#10s    → 10.000 s
```

当`10.000`显示为`######`时，不仅要增加控件宽度，还要把“域长度”增加到能够容纳符号、整数位和小数位。

## 六、三方联调结果

本次已经验证：

- PLCSIM Advanced虚拟CPU能够正常下载并进入RUN；
- Factory I/O能够读取PLC输出并写入两个传感器信号；
- WinCC能够通过符号变量读写`DB_C2_Control`；
- HMI自动模式、启动、停止、故障复位、计数清零和模拟急停均完成配置；
- 设备状态灯、系统状态灯、当前步号、步骤文本和工艺参数能够动态显示；
- GRAPH可以执行进瓶、稳定、灌装、滴漏、出瓶和完成步骤；
- HMI、PLC与Factory I/O之间形成了完整的数据链路。

## 七、暴露出的GRAPH逻辑问题

项目最后的主要问题出现在S50出瓶和S60完成之间。

原逻辑在出口传感器检测到瓶体时，从S50切换到S60；但`xSeqConveyorReq`只在S50有效，离开S50后输送请求立即消失。结果是瓶体可能正好停在第二个传感器处，没有真正离开检测区域或进入移除器。

更合理的思路应当是：

1. S50负责把瓶体送到出口传感器；
2. S60继续保持输送带运行并产生一次计数；
3. 只有当出口传感器从1恢复为0，确认瓶体已经离开后，流程才返回S0；
4. 对停止、急停、报警后的步骤恢复策略进行单独设计，而不是只依赖重新按启动按钮。

这次问题说明，顺控程序不能只考虑“传感器检测到了什么”，还要考虑执行器在步骤切换瞬间是否继续保持、工件是否真正离开，以及异常中断后如何恢复。编译0错误只代表语法和组态通过，不代表工艺逻辑正确。

## 八、这次真正学到的内容

- 用GRAPH拆分工艺步骤、动作和转换条件；
- 理解步骤`N`动作离开步骤后会立即撤销；
- 用LAD处理模式、联锁、报警、计数和最终输出；
- 使用PLCSIM Advanced连接Factory I/O；
- 从空白场景搭建输送带、传感器、Emitter和Remover；
- 建立PC站`IE General`、PN/IE子网和指定HMI连接；
- 使用WinCC符号变量、按钮事件、动态外观和文本列表；
- 正确显示并输入PLC的`TIME`参数；
- 根据HMI、PLC在线值和Factory I/O动作共同定位问题；
- 接受“程序能运行”和“工艺逻辑成熟”之间仍有明显差距。

## 总结

C2不是一个逻辑完全成熟的成品，但它完成了本阶段最重要的学习目标：第一次把PLC程序、虚拟产线和HMI监控连接成一个整体，并在联调中真正遇到通信、变量、显示格式、按钮事件和工艺转换问题。

相比单纯照着程序输入，最后暴露出的GRAPH问题更有价值。它让我认识到，顺序控制的核心不是把步骤画出来，而是确保每个步骤的进入条件、保持动作、离开条件和异常恢复都与真实工件运动一致。
